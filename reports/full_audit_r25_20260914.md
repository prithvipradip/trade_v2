# §1 — ARCHITECTURAL FINDINGS (the holistic pass)

These are not reachable from any per-file sweep. They are the round's headline, because they
explain why 24 rounds and ~465 instance-fixes have not stopped the bleeding.

## arch-01-broker-boundary-does-not-exist  [design | ops_reporting | live_path=True]

**Where:** `src/ait/broker/ibkr_client.py:58` (the `.ib` property); ~40 call sites across
`bot/orchestrator.py` (11), `execution/executor.py` (9), `data/market_data.py` (8),
`data/options_chain.py` (5), `execution/reconciler.py` (3), `execution/portfolio.py` (3),
`broker/account.py` (1)

**Claim:** `IBKRClient` is not a boundary. It publishes the raw `ib_insync` handle as a public
property and seven modules reach past it. There is **no `reqMktData` wrapper at all** — instead
six independent copies of the request/settle/cancel dance (`executor.py:687,703` ·
`orchestrator.py:2986,3143,3434` · `reconciler.py:152,162` · `options_chain.py:701,748` ·
`market_data.py:355,364,529,538`), and `reqMarketDataType` is set from two places
(`ibkr_client.py:121` at connect, `market_data.py:528` per call).

**Evidence:** enumeration is reproducible —
`grep -rn "\.ib\." src/ait --include="*.py" | awk -F: '{print $1}' | sort | uniq -c`
returns the seven-module distribution above.

**Consequence:** there is no single place where broker I/O can be retried, rate-limited,
logged, or faked for tests. Each of the six copies drifts independently — which is exactly what
produced the 2026-09-14 `snapshot=True` defect, where one of six had diverged and silently
returned no `modelGreeks` for months. **That fix closed the instance; the generator is untouched.**

**Suggested fix:** one `IBKRClient.market_data()` wrapper owning request/settle/cancel and the
data-type decision; demote `.ib` to `_ib` and migrate call sites incrementally. Not a rewrite —
a single seam that makes the next divergence impossible.

## arch-02-state-boundary-does-not-exist  [design | ops_reporting | live_path=True]

**Where:** `src/ait/bot/state.py` (nominal owner, 31 connects) vs. direct `sqlite3.connect` in
`data/historical.py` (20), `learning/analyzer.py` (3), `monitoring/analytics.py` (2),
`reporting/go_live.py`, `monitoring/ops_health.py`, `monitoring/duckdb_analytics.py`,
`ml/meta_label.py`, `config/runtime_env.py`, `dashboard/app.py`,
`dashboard/walkforward/export.py`, `orchestration/master.py`, `status.py`, plus 8 `scripts/`

**Claim:** `StateManager` nominally owns the database, but 13 modules and 8 scripts open the
same files directly. Schema knowledge is therefore duplicated across the tree with no owner.

**Evidence:** `state.py:194-266` holds the only migration mechanism — a 12-entry `ALTER TABLE`
tuple wrapped in `except sqlite3.OperationalError: pass`, which cannot distinguish "column
already exists" (benign) from "no such table" (a lost migration). The file's own comment at
`:249-253` records a past incident where exactly that swallowed a real failure.
**There is no `schema_version` or `PRAGMA user_version` anywhere in the repo.**

**Consequence:** no migration can ever be enforced, because no component owns the schema. This
is the root of the DuckDB mirror divergence (`duckdb_analytics.py:127-208` has six
`CREATE TABLE IF NOT EXISTS` and **zero** `ALTER TABLE`, so an existing mirror keeps its old
shape forever while SQLite gains columns, with no detector).

**Suggested fix:** a `schema_version` table and one owning module; every other reader opens
read-only (`mode=ro`) and is refused write access by construction.

## arch-03-layering-is-cyclic  [design | ops_reporting | live_path=True]

**Claim:** the internal import graph contains mutual cycles **bot ↔ execution**, **bot ↔ risk**,
**bot ↔ reporting**, plus `ml → execution` and `ml → optimization`.

**Evidence:** reproducible per-package import extraction shows `execution → bot`, `risk → bot`,
and `reporting → bot` back-edges against `bot → {execution, risk, reporting, …}`.

**Consequence:** importing any leaf can drag the broker stack into a process that has no
business with it. The 2026-09-14 Streamlit crash (`dashboard → go_live → strategies/base →
options_chain → market_data → ib_insync`, whose `eventkit` calls `asyncio.get_event_loop()` at
import time) was a symptom. The ledger's own account shows the **first fix was wrong** and the
second *worked around* the cycle by moving a constant — the cycle itself is still there, and
`strategies/__init__.py`'s eager `from ait.strategies.base import …` still makes every submodule
import heavy.

**Suggested fix:** make the back-edges type-only (`if TYPE_CHECKING:`) and empty
`strategies/__init__.py`. An import-linter contract in CI pins it thereafter.

## plat-01-w13-gateway-recovery-is-inert-and-its-escalation-can-never-fire  [bug | live_money | live_path=True]

**Where:** `src/ait/orchestration/master.py:432-436`, escalation at `:422-431`

**Claim:** W13 (2026-09-08) exists to end the absorbing state where a wedged Gateway leaves open
positions with no exit engine — it materialized twice, once for 3h25m inside RTH. On this host
the recovery is inert **and its human-escalation backstop is unreachable**, because the early
return at `:433-435` precedes `self._gateway_recoveries += 1` at `:436`. The counter never
increments, so `if self._gateway_recoveries >= GATEWAY_MAX_RECOVERIES` can never be true.

**Evidence (execution probe, this host):**
```
GATEWAY_START_SCRIPT : C:\IBC\StartGateway.bat
os.path.exists(...)  : False        -> early return before the counter
_gateway_process_alive() -> False   (silently; see plat-02)
```

**Trigger:** any wedged Gateway on this host. **Consequence:** the absorbing state W13 was
written to end is restored, with open positions and no exit engine; the escalating page never
arrives. (Partial mitigation: the separate 30-min `_alert` at `:697-703` still pages "Gateway
unreachable, start deferred" — so not silent, but the escalation is dead.)

**Why no test caught it:** `tests/test_w13_gateway_recovery.py` patches
`M.os.path.exists → True` at `:55,76,88,111,148,170` and stubs `_gateway_process_alive`
at `:54,75,87,110,147,169`. **The 177-line test file passes green on macOS while the mechanism
it tests is inert on macOS.**

**Suggested fix:** increment before the availability check, or resolve the start script per
platform and fail closed with a page when none exists.

## tz-01-hour_of_day-is-an-ml-feature-stamped-from-the-host-clock  [bug | research_validity → live_money when armed | live_path=True]

**Where:** `src/ait/bot/orchestrator.py:1579` (live inference) and `:3108` (`trade_context`
labeling); training side `src/ait/ml/meta_label.py:536`; constants
`meta_label.py:435` and `backtesting/engine.py:634`

**Claim:** `hour_of_day` is a member of `META_FEATURES` (`meta_label.py:96`) produced from
**four sources with three conventions**:

| Source | Value | Convention |
|---|---|---|
| `orchestrator.py:1579` `dt.now().hour` | live inference | naive local — **CEST on this host** |
| `orchestrator.py:3108` `float(datetime.now().hour)` | persisted label context | naive local — **CEST** |
| `meta_label.py:536` `entry_hour` from stored `entry_time` | training corpus | **ET for pre-move rows, CEST after** |
| `meta_label.py:435`, `engine.py:634` hardcoded `10` | backtest rows | ET-open, constant |

**Evidence:** on the Windows (ET) host, RTH maps to `hour_of_day ∈ {9..16}`. On this CEST host
the *same market hours* map to `{15..22}`. Verified: ET 09:30 → CEST 15:30; ET 16:00 → CEST 22:00.

**Consequence:** every row written from this host carries an `hour_of_day` six higher than the
historical corpus. A model trained on the mixed corpus learns a split encoding *which machine
wrote the row*, not time of day. The feature reaches a live veto —
`orchestrator.py:1583` `self._meta_labeler.predict(meta_context)` → `:1584` `not take_trade`
→ `return` at `:1601`.

**Severity note (honest):** the meta-labeler is currently **untrained and default-off** (the
ledger's dormant inventory; `predict()` returns `None`, so `:1584` is inert). This is
`research_validity` **today** and becomes `live_money` the moment it is armed — which the
file's own comments schedule at 100+ closes. Register it now, because arming it later on a
contaminated corpus is the failure mode.

**Suggested fix:** derive `hour_of_day` from `now_et().hour` at all four sites, and restate or
fence rows written between the migration and the fix.

## qual-01-outlier-anchor-is-last-seen-not-last-known-good  [bug | ops_reporting | live_path=True]

**Where:** `src/ait/data/quality.py:106-108`, against the comment at `:47`

**Claim:** `:47` declares *"Track last known good prices for outlier detection"*, but `:106-108`
updates `_last_prices[symbol] = last` unconditionally whenever `last > 0` — **including when the
quote was just judged invalid**. The anchor is therefore poisoned by exactly the outlier it
exists to catch.

**Evidence:** `is_valid` is computed at `:110`, *after* the update at `:106-108`; nothing
consults it. A bad print at $500 on a $100 underlying is flagged (correct), then stored; the
next *good* $100 tick is flagged as a second jump (500→100) and stored in turn.

**Consequence:** on the live exit path (`execution/portfolio.py:174`) one bad tick yields **two
consecutive `degraded` verdicts**, and `degraded` withdraws the touch stop's authority — the
primary loss cap on a credit position — for two cycles instead of one.
`tests/test_data_quality.py:125-128` exercises a single jump and cannot see this.

**Suggested fix:** move the update below `:110` and gate it on `is_valid`.

## qual-02-staleness-timestamp-uses-a-falsy-zero-test  [bug | ops_reporting | live_path=True]

**Where:** `src/ait/data/quality.py:63` — `ts = timestamp or now`

**Claim:** `0.0` is falsy, so a feed reporting epoch-0 (a common "no time" sentinel) is read as
*"caller passed no timestamp"* → `staleness = 0.0` → the stale-quote check at `:67` cannot fire.
A zeroed feed timestamp is precisely the pathology the gate exists for.

**Consequence:** narrow (requires exactly `0.0`) but the failure direction is open.
**Suggested fix:** `ts = now if timestamp is None else timestamp`.
