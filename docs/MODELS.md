## 1. The models at a glance

Each model answers one question. The tree models are gradient-boosted trees (XGBoost and LightGBM, blended) that run on CPU; no deep-learning framework is used.

| Model | Question it answers | Live bot | Research |
|---|---|---|---|
| Direction ensemble (`ml/ensemble.py`) | Over the label horizon, up, down or flat, and how confident? | Predicts every scan; entry context, directional strategies, drift tracking | Trained per window |
| Range model (`ml/range_predictor.py`) | P(price stays inside the band the condor sells, over its hold) | The condor's confidence in enforce mode; logged and stored on every trade in observe mode | Trained per window; decides the range gate when `gates_mode` is `enforce` |
| Vol-magnitude model (`ml/vol_magnitude_predictor.py`) | P(a big move) | Trained daily; used only by long-volatility structures, which are not enabled | Not trained |
| Meta-labeler (`ml/meta_label.py`) | Given the signal and the market state, will *this* trade be profitable? | Disabled; the code path and its guards exist | Trained per window after the optimizer |
| Regime classifier (`ml/regime.py`) | Which of seven regimes is the market in? | Entry override, thesis check, recorded on each trade | Not used (the engine has its own thresholds, `backtest.regime_*`) |
| Drift detector (`ml/drift.py`) | Is the direction model getting worse live? | Off | Not used |

A model is chosen for the **payoff** of the structure it gates: an iron condor is paid for the price *staying put*, so it is gated by the range model, not by a direction model. For the same reason the
minimum directional confidence does not veto a condor.

**Per-symbol models.** The direction and the binary models are trained per symbol, with a fallback model for a symbol that has none of its own. The ensemble blends XGBoost and LightGBM with `ml.ensemble_weights`; the
range model instead fits its member weights from each member's cross-validated edge over a coin flip, and a member with no skill gets zero weight.

## 2. Features

**What goes in.** One feature frame per symbol, computed from daily OHLCV and context by [`ml/features.py`](../src/ait/ml/features.py): momentum, volatility, volume, trend, price action, multi-timeframe, implied-vol regime, market
structure, cross-asset (VIX, relative strength against SPY, correlation), macro (yield curve, dollar), seasonality and fractal / multi-scale measures, plus a block of intraday session features when 5-minute data exists. Every
feature is **stationary** (ratios, slopes and normalised levels; no raw price levels), so the models generalise across price levels. A column that is entirely missing (for example a degraded feed) is neutral-filled
with a warning rather than allowed to wipe out every row.

**The catalogue.** `config/feature_names.py` holds the complete list, in the model's fixed column order. The same names, each with an on/off switch, are listed under `ml.features.<group>.use` in `config.yaml`.

### 2.1 Switches

Each feature has a `true`/`false` switch under `ml.features.<group>.use`. `true` makes the column an input of the direction, range and vol-magnitude models and of the retrain's hyperparameter search; `false` leaves it out. The column is
**still computed** either way, because the meta-labeler, the entry gates and the dashboards read some columns from the same frame; so a switch does not shorten the warm-up (the IV rank needs its full history whatever the switch says),
and the meta-labeler's own inputs do not change. The shipped switches reproduce the original model list exactly; five columns that are computed but were never model inputs (`put_call_proxy`, `vix_term_structure`, `skew_proxy`,
`momentum_divergence`, `range_compression`) ship off so a study can try them.

Switches are a mapping, not a list, on purpose: a study or overlay is laid over `config.yaml`, and mappings merge key by key while a list would replace the whole list, so dropping one feature would mean copying every name. A study writes
one line, for example `ml: {features: {fractal: {use: {hurst_psd_divergence: false}}}}`. A switch is keyed by its role (`rsi_long`, not `rsi_14`) so a window change never renames it. An unknown key, a feature under the wrong group, or
switching every daily feature off is a startup error that lists the valid names.

### 2.2 Windows

The indicator windows are settings in the same groups. Twenty-seven model columns carry a window in their name (`rsi_14`, `price_vs_sma_20`, `above_sma200`, `vix_change_5d`...), so changing a window also **renames** the column
(`rsi_long: 21` turns `rsi_14` into `rsi_21`); the meta-labeler's inputs, the engine's meta-context keys and the entry-signal snapshots follow. The intraday column names are a fixed list and do not follow their windows
(`intraday_momentum_1h` then means `hour_bars` bars). Clip bounds, neutral values, the wavelet family, the multifractal scales, the seasonality encoding and the 252-day annualisation constant are algorithm constants, not settings.

**Constraints enforced at load** (a violation is a startup error): ordered pairs (`rsi_short < rsi_long`, `macd_fast < macd_slow`, `roc_short < roc_mid < roc_long`, `rv_short < rv_long`, `sma_fast < sma_mid < sma_slow`,
`volume_fast_window < volume_avg_window`, and `vol_regime.fast < rv_short < rv_long < vol_regime.slow`); every `*_min_periods` at most its window; derived column names must be distinct and must not collide with a fixed column. Very short RSI
periods make RSI undefined whenever a window has no down days, and those rows are dropped.

**Warm-up and context.** The longest look-back among the daily windows (252 rows at the defaults, the IV-rank range) is what a research test window needs in front of it, so its features match the ones the model trained on
(`FeatureSpec.longest_lookback()`, checked against `backtest.walkforward_tuning.oos_feature_context_bars`).

## 3. Labels and validation

**Labels.** *Direction:* the forward return over a horizon of a few days, against a threshold, becomes bullish, bearish or neutral. *Range:* did the price stay inside the band over the hold; the band is `ml.range_threshold_pct` (a fixed ±5% by default, the wing width the
live condor sells), and the horizon is the **reachable** hold (the entry DTE minus the days before expiry at which a credit structure is closed), with one definition for live and research (`ml/range_spec.py`). *Vol-magnitude:*
did the price move beyond a larger band over its horizon.

**Validation.** Models are validated walk-forward: every validation fold sits after its training data, with a **purge gap** at least as long as the label horizon so overlapping labels cannot leak into the score. The skill reported is
balanced accuracy (a coin flip is 0.50). A binary model is used **only if its cross-validated edge over the base rate is at least a minimum**; below that its `predict` returns nothing, and in enforce mode a missing range
prediction blocks condor entries (fail closed). A retrained direction model is **rolled back** if its average cross-validated accuracy fell by more than `ml.rollback_margin`. Class-balance guards warn when a binary label is
nearly constant and refuse to train with too few rows of either class.

## 4. Hyperparameters

## 5. Saved models

Models are pickles under `models/`: `ensemble.pkl`, `range.pkl`, `vol_magnitude.pkl`, `meta_label.pkl`, timestamped `ensemble_v-<date>-<time>.pkl` versions (the number kept is `ml.model_versions_kept`, also how far back a rollback can
go), and a research sandbox in `models/research/` that a research run uses instead of these files. Every saved model carries a **spec record**: the hyperparameters it was trained with, the **feature-spec hash**, and (range and
vol-magnitude) the band and horizon. What a mismatch does:

| Mismatch between the saved model and the current settings | Result |
|---|---|
| Hyperparameters | The model is served; `model_spec_mismatch` is logged with the differences |
| Feature windows or switches (the feature-spec hash) | The model is **refused** (`model_feature_spec_mismatch`, critical) and retrained, because it would predict on silently zero-filled columns |
| Range or vol-magnitude band / horizon | Flagged critical and retrained |
| A model with no recorded spec (saved before specs existed) | Treated as having the original defaults, so today's files keep loading while the settings are at their defaults |

The feature-spec hash covers the windows and the switches, but a window group or a switch enters it **only when a value differs from its default**, so at the shipped settings the hash is unchanged and nothing is refused or
retrained when settings are merely listed. The research engine also drops a predictor whose hash differs from its own feature frames.

## 6. The retrain

A supervisor job retrains every trading morning (schedule in [GUIDE.md](GUIDE.md) section 3). It uses its **own IB session** (`ml.retrain_ib_client_id`), takes daily bars from IB only, fetches every series before writing anything, and aborts
cleanly if IB is down, so a bad data day cannot overwrite good models. After that pre-flight it refreshes the stored implied-vol history from the same session, trains, writes the models and drops a marker; the supervisor then restarts the bot once
(never during market hours or the post-market window) so it loads the new files. The bot also checks at startup and pre-market whether models are due: untrained, a spec mismatch, `ml.retrain_interval_days` elapsed, or (if
enabled) drift. If the retrain fails or hangs the models simply stay as they were and an alert is sent ([RUNBOOK.md](RUNBOOK.md) "Alert → action").

## 7. The models one by one

**Direction ensemble.** Three classes (bearish, neutral, bullish) with a confidence. At entry its confidence is blended with the multi-timeframe adjustment; in observe mode it never vetoes a condor. It is the only model the drift
detector watches.

**Range model.** P(stays in range). Trained per symbol; skipped (no prediction) when its cross-validated edge is below the minimum. The live spec (band and horizon) is defined once in `ml/range_spec.py`. Every scan stores its verdict,
including its absence, on the trade row so the observe-mode record can be scored later.

**Vol-magnitude model.** P(big move). Used only by long-volatility structures; trained daily so it is ready if one is enabled.

**Meta-labeler.** A second model trained on the bot's own closed trades and their entry snapshots (20 inputs; a missing input takes the neutral value in `ml.meta_label_neutrals`). It is **disabled**. Even when enabled it acts only
outside paper-trading mode, once trained, and once the real-close count reaches `meta_label.min_closes_to_enable`. The arm guards (`min_feature_coverage`, `max_artifact_age_days`) stop a model trained on mostly-empty snapshots or a stale
file from being armed.

## 8. The regime classifier

From the last `min_history_rows` or more days of SPY plus VIX it labels the market as one of seven regimes (high volatility, IV crush, mean-reverting, low volatility, trending up, trending down, range-bound) with a confidence. It is
rule-based, not trained. Where the live bot uses it: **entry**, where a high-volatility label at or above `ml.regime_override_confidence` forces the direction to neutral (moot for condors, which ignore direction); the **thesis check** for
directional positions (a trending position that now reads as high volatility above `exit.thesis_regime_shift_confidence` is flagged); and as a **record** (`entry_regime`) on each trade.

The trend strength (-1 to +1) is the average of three kinds of terms, each clamped to [-1, 1]: moving-average slopes, the price's distance from moving averages, and the recent return. The IV rank here is a price-only proxy (where today's
20-day realised volatility sits between the lowest and highest such values over the last `regime.iv_rank_window_rows`, 252 by default; 0 to 1); it is not the stored-IV rank (`ait.data.iv_rank`) and not the `vol_regime` feature, which are separate on purpose. `high_vol_confidence_floor` and
`ml.regime_override_confidence` must agree: keep the override threshold at or below the floor, because a day triggered by VIX alone scores exactly the floor.

## 9. The drift detector

The live bot compares the direction model's calls with what happened; if the model is clearly getting worse it asks for an early retrain instead of waiting for the schedule. It is **off by default** (`ml.drift_detection_enabled`):
an outcome is recorded only when a *directional* trade closes, so a book of iron condors never completes a sample and the detector could never speak. Turn it on (and restart) only if directional strategies trade. On drift the report says
"retrain", the trainer's `needs_training` returns true, and the next opportunity retrains; a retrain clears the window.

## 10. Gating: observe and enforce

`ml.entry_gates_enabled` decides whether the models can **veto** a live entry.

| | Enforce (`true`) | Observe (`false`, the shipped mode) |
|---|---|---|
| Range model | Its probability replaces the condor's confidence; a floor applies; a missing prediction blocks the entry | Logged and stored on the trade; never blocks. The condor is validated on a configured direction-neutral baseline confidence |
| Fractal regime veto | Acts | Logged as "would block" |
| Vol-magnitude model | Replaces a long straddle's confidence | Same |
| Meta-labeler | Acts only if enabled, trained and sufficiently evidenced | Not used |

**Why observe.** A binary model whose cross-validated edge is below its minimum returns no prediction, and under enforce a missing range prediction blocks every condor entry, so the track record stops growing. Observe keeps entries flowing
while the stored verdicts show whether the gate would have helped. Flipping the setting is an operator decision after a pre-registered test recorded in `PLAN.md`.

**Research.** The research engine enforces the gates (`backtest.gates_mode: enforce`), which is one of the deliberate research-versus-live differences that the parity manifest prints ([RESEARCH_GUIDE.md](RESEARCH_GUIDE.md) section 11).

## 11. Changing a model setting

| You change | Live | Research |
|---|---|---|
| A hyperparameter | Edit `config.yaml`; applies at the next retrain and restart; old models are served with a logged mismatch | Put it in a study or the overlay; the parity manifest warns (`ml_hyperparams`) |
| A feature window or switch | Edit `config.yaml`; at the next start every saved model is refused and retrained (`model_feature_spec_mismatch`, critical, on the first load; one retrain). Do it outside market hours, run `scripts/smoke_deploy.py` first; rollback is reverting the line (and one more retrain) | Put it in a study or the overlay; the parity manifest warns (`ml_features`); the run record stores the resolved feature list and the hash |
| A label constant | Edit `config.yaml`; the next retrain rebuilds the model (`range_model_spec_mismatch`) | Shared keys follow live unless overridden |
| Drift or regime settings | Edit `config.yaml`; applies at the next bot restart | Not used by research |
| The gate mode | The operator's decision (see the confirmation list in [TECHNICAL_GUIDE.md](TECHNICAL_GUIDE.md)) | `backtest.gates_mode` in the overlay |

Never edit `config.yaml` for an experiment: a study (or the overlay) writes only the difference, and the live bot never loads it. To add a new feature, see [TECHNICAL_GUIDE.md](TECHNICAL_GUIDE.md) ("Adding a feature").
